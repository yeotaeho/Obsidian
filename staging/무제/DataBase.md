# 데이터베이스 — 데이터 흐름과 SQLAlchemy · Alembic · Vector DB

데이터가 애플리케이션을 흐르는 경로부터, 파이썬에서 DB를 관리하는 SQLAlchemy/Alembic, 그리고 AI 검색을 위한 Vector DB까지 정리했습니다.

## 1. 데이터 흐름

데이터는 다음 경로로 흐르며, 각 단계에서 기존 데이터와 비교됩니다. 기존 데이터는 **엔티티**가 가져오고, 사용자가 입력한 값은 **DTO**에 담겨 레포지터리에서 비교됩니다. 이때 DB에 추가할지 말지를 결정합니다.

```
타임리프(값 입력)
  → 컨트롤러(값을 DTO에 담음)
  → 서비스
  → 레포지터리(DB에서 온 엔티티와 DTO 비교 후 저장/배출 결정)
  → DB
```

데이터 파일은 `resources/static`에 저장할 파일을 만들어 기입하고, Gradle에서 파일 확장자에 따라 컨트롤러로 옮길 수 있게 합니다.

로컬에서 만든 DB를 클라우드로 올릴 때는 다음 서비스를 사용했습니다.

- **Neon**
- **Upstash**

## 2. SQLAlchemy — 파이썬 코드 ↔ SQL 통역

> **SQLAlchemy와 Alembic은 파이썬에서 DB 관리의 핵심 라이브러리입니다. 스프링의 JPA 같은 존재인데, 자동 수정·추적까지 가능한 업그레이드 버전이라고 보면 됩니다.**

SQLAlchemy는 테이블을 설계하고 통역하는 라이브러리입니다. 핵심 기능인 `Base`로 파이썬 코드를 통해 테이블을 정의하고 DB 연결 기능을 만듭니다.

이후 어떤 종류의 DB(PostgreSQL, MySQL 등)를 쓸지, 접속 주소는 무엇인지를 **SQLAlchemy Engine**을 통해 설정합니다. 그러면 SQLAlchemy가 파이썬 코드로 작성한 테이블 정보를 DDL/DML/DQL/DCL 등 쿼리문으로 바꿔(통역) 줍니다. 최종적인 생성·자동 업데이트 관리는 Alembic으로 처리합니다.

## 3. Alembic — 테이블 변경 이력 관리

Alembic은 테이블을 **수정·관리·추적**까지 해 주는 라이브러리입니다. 히스토리(기록)를 통해 현재·이전·미래 테이블을 관리합니다.

- 이전 기록으로 현재 테이블을 수정하다 오류가 나면 이전 테이블로 복귀할 수 있습니다.
- "이번에 `email` 컬럼이 추가됐네"라는 내용을 담은 수정 전용 DDL 스크립트를 생성할 수도 있습니다.

이렇게 하면 전체적인 공사 순서가 꼬이지 않습니다.

> **테이블 생성은 SQLAlchemy로도 가능하지만 히스토리가 남지 않아 수정이 불가합니다. 그래서 Alembic을 사용해 히스토리를 남겨 수정 가능하게 합니다.**

| 구분 | SQLAlchemy | Alembic |
| --- | --- | --- |
| **주요 임무** | 파이썬 코드 ↔ SQL 통역 | DB 구조 변경 이력 관리 및 적용 |
| **생성(Create)** | 최초 1회 생성 가능 | 마이그레이션 파일로 생성 가능 |
| **수정(Update)** | 불가능(직접 못함) | 전문 분야(Alter Table 전문) |
| **삭제(Drop)** | 전체 삭제는 가능 | 특정 컬럼/테이블만 골라 삭제 가능 |

주요 명령은 다음과 같습니다.

```bash
# 마이그레이션 파일 생성
alembic revision --autogenerate -m "Add pref_domain_json and value columns"

# 데이터베이스 테이블 업데이트 (실제 SQL 실행)
alembic upgrade head
```

## 4. Vector DB와 임베딩

Vector DB는 기존의 PostgreSQL DB를 **에이전트가 알아들을 수 있게 임베딩한 DB**입니다.

### HNSW 인덱스

베이스 테이블을 전부 임베딩 테이블로 구성하면 CRUD가 느려진다는 단점이 있는데, 이를 극복하기 위해 **HNSW(Hierarchical Navigable Small World)** 인덱스를 사용합니다.

**1) 핵심: 다층 그래프 구조**
HNSW는 데이터를 단순 나열하지 않고 여러 층의 계층형 그래프로 만듭니다. 상위 층으로 갈수록 노드 수가 적고 노드 간 거리가 멀어(고속 이동), 하위 층으로 갈수록 데이터가 밀집해 세밀한 탐색이 가능합니다. 쿼리가 들어오면 최상위 층에서 '성긴' 탐색으로 목표 근처로 빠르게 이동한 뒤, 아래 층으로 내려가며 정교하게 찾습니다. 덕분에 데이터가 수백만 건이라도 전수 조사(Flat Search) 없이 **로그 시간 복잡도(O(log N))**에 수렴하는 속도를 보장합니다.

**2) CRUD 지연·자원 단점 극복**
"CRUD가 느리다"는 점은 주로 인덱스 업데이트(C/U/D)에서 발생합니다. 새 데이터를 추가할 때마다 적절한 층에 노드를 배치하고 주변 노드와의 연결(Edge)을 계산해야 하므로 연산량이 IVFFlat보다 많고, 그래프 연결 정보를 메모리에 상주시켜야 해 RAM도 많이 씁니다. 다만 HNSW는 **학습(Training) 단계가 없어** 실시간으로 인덱스를 갱신할 수 있고, 최근에는 PQ(Product Quantization)로 벡터를 압축하거나 고성능 NVMe SSD를 활용해 자원을 최적화합니다.

**3) IVFFlat vs HNSW**

| 구분 | IVFFlat | HNSW |
| --- | --- | --- |
| 인덱스 구조 | 클러스터링(군집화) | 계층형 그래프 |
| 사전 학습 | 필요(데이터가 쌓인 후 생성) | 불필요(빈 테이블에도 생성) |
| 검색 속도 | 빠름(데이터 분포 영향) | 매우 빠름(안정적) |
| 메모리 효율 | 우수 | 낮음(많은 RAM 소모) |
| 정확도(Recall) | 보통 | 매우 높음 |

**4) "학습 단계가 없는 것"이 장점인 이유**
IVFFlat은 전체 데이터를 먼저 훑어 그룹(Centroids)을 나누는 Training이 필수라, 데이터가 적을 때 만든 인덱스는 데이터가 늘면 검색 품질이 급락합니다. 반면 HNSW는 데이터가 하나도 없을 때 인덱스를 먼저 정의해 두고 데이터가 들어올 때마다 노드를 하나씩 추가하므로, **데이터가 수시로 추가/삭제되는 동적 서비스에서 운영 효율이 훨씬 높습니다.**

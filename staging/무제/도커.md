> **도커는 앱 실행에 필요한 모든 환경(코드, 라이브러리, 설정)을 하나의 '컨테이너'에 담아 어디서든 똑같이 실행되게 해 주는 도구입니다.**

## 3. WSL이 하는 일 — Windows와 Linux 연결

지금까지 파워셸과 터미널에서 한 작업은 모두 **Windows와 Linux를 파이프로 연결**하기 위한 것이었습니다. WSL(Windows Subsystem for Linux)은 Windows라는 "땅"에 파워셸을 설치해 Linux라는 "다른 땅"에 연결하는 파이프라인을 만드는 행위라고 이해했습니다.

> 비유하면 — **땅: 커맨드 / 통로: 파워셸 / 다른 땅: 터미널(Linux)**.

객체 생성에 빗대면 다음과 같습니다.

```
클래스 인스턴스 = new 클래스();
이미지   컨테이너 = new 이미지();
//  타입            주소
```

## 5. PostgreSQL에 CSV 데이터 넣기

전체 흐름은 다음과 같습니다(테이블을 먼저 만들어야 합니다).

**1) 컨테이너 접속** — CSV 복사나 psql 실행을 위해 컨테이너 내부에 접근합니다.
```bash
docker exec -it <컨테이너이름> bash   # 예: cogirihub
```

**2) PostgreSQL 접속** — psql CLI로 들어가야 SQL을 실행할 수 있습니다.
```bash
psql -U <사용자명> -d <데이터베이스명>   # 예: psql -U cogirihub -d cogirihub
```

**3) 테이블 생성** — 컬럼 타입이 CSV 값과 맞는지 확인해야 합니다(생략하면 삽입 시 타입 에러 발생 가능).
```sql
CREATE TABLE weather (
    id SERIAL PRIMARY KEY,
    date DATE,
    avg_temp FLOAT,
    max_temp FLOAT,
    max_temp_time TIME,
    min_temp FLOAT,
    min_temp_time TIME,
    diff_temp FLOAT,
    precipitation FLOAT
);
```

**4) CSV를 컨테이너 안으로 복사** — 호스트(내 컴퓨터)에서 실행합니다.
```bash
docker cp "C:\path\to\weather.csv" <컨테이너이름>:/weather.csv
```

**5) CSV 데이터 삽입** — 컨테이너 안 psql에서 실행합니다. CSV 컬럼 순서와 테이블 컬럼 순서가 정확히 맞아야 합니다.
```sql
\copy weather(date, avg_temp, max_temp, max_temp_time, min_temp, min_temp_time, diff_temp, precipitation) FROM '/weather.csv' DELIMITER ',' CSV HEADER;
```

**6) 데이터 확인**
```sql
SELECT * FROM weather ORDER BY id;
```

> **핵심 포인트(놓치기 쉬운 부분)**
> 1. CSV 컬럼과 테이블 컬럼의 타입·순서 일치
> 2. 빈 값 → `NULL` 처리
> 3. `docker cp`로 올린 컨테이너 내부 경로 확인
> 4. `\copy` 사용 시 `DELIMITER`, `CSV HEADER` 등 옵션 정확히 명시
> 5. 테이블 생성 후 필요하면 기존 데이터 삭제(`TRUNCATE`)

## 6. MSA와 컨테이너, 그리고 대체재

> **마이크로서비스(MSA) 환경에서는 컨테이너 기술이 사실상 필수에 가깝습니다.** 다만 "도커 자체"가 필수라기보다 "컨테이너 런타임"이 필수이고, 그중 가장 대중적인 표준이 Docker일 뿐입니다(CRI-O, Podman 등도 있음).

| 상황 | 추천 도구 |
| --- | --- |
| Docker와 거의 동일한 것을 원함 | Podman |
| 쿠버네티스 환경 사용 | containerd, CRI-O |
| Mac에서 Docker Desktop이 느림 | OrbStack, Colima |
| Docker Desktop의 무료 정책이 싫음 | Rancher Desktop, Podman |
| 완전한 VM 환경 필요 | VirtualBox, VMware |

## 7. docker-compose의 `${변수}` 치환 vs `env_file`

<!-- TODO: 이미지 업로드 필요 -->
![[Pasted image 20260102123611.png]]

### 실제 문제
`${변수명}` 치환이 `env_file`의 내용을 참조하지 않기 때문에 값이 비는 문제가 생깁니다.

### 실행 순서
1. **파싱 시점(호스트에서)**: `docker-compose.yaml`을 읽고 `${변수명}` 치환을 처리합니다. 참조 대상은 **호스트 환경 변수** 또는 `docker-compose.yaml`과 같은 디렉터리의 `.env` 파일이며, 이 시점에 `env_file`의 내용은 사용되지 않습니다.
2. **런타임(컨테이너 시작)**: 컨테이너가 시작될 때 `env_file` 내용이 컨테이너 내부 환경 변수로 주입되고, `environment` 섹션의 (이미 치환된) 값들이 설정됩니다.

```
docker-compose.yaml 파싱 (호스트)
  ├─ ${UPSTASH_REDIS_HOST} 치환 시도
  │   └─ 참조: 호스트 .env 파일 (docker-compose.yaml과 같은 디렉토리)
  │   └─ 참조 안 함: env_file의 ../.env 파일
  └─ 결과: SPRING_REDIS_HOST="" (비어있음)

컨테이너 시작 (런타임)
  ├─ env_file: - ../.env 읽기 → 컨테이너 내부에 환경 변수 주입
  └─ environment: 이미 치환된 값들 주입 → SPRING_REDIS_HOST="" (이미 비어있음)
```

### 설계 철학
- `${변수명}` 치환: 템플릿화와 구성 파일의 동적 생성(호스트 측)
- `env_file`: 런타임 환경 변수 주입(컨테이너 측)

### 결론
순서가 엇갈려서가 아니라, **`${변수명}` 치환이 `env_file`을 참조하지 않기 때문**입니다. `${변수명}` 치환은 호스트의 환경 변수나 같은 디렉터리의 `.env` 파일에서만 값을 읽습니다.

AI 에이전트 시스템을 설계하면서 마주친 핵심 개념들(온톨로지, MCP, 에이전트, 커플링)을 정리했습니다.

## 1. 온톨로지(Ontology) — 모델 구조

온톨로지는 **모든 것을 통합한 하나의 일관된 관점 구조**입니다. 프론트엔드의 스토어와 비슷한 역할이라고 이해했습니다.

## 2. MCP (Model Context Protocol)

> **MCP는 멀티탭 같은 존재입니다. 예전에는 하나하나 따로 연결해야 했다면, MCP는 플러그만 꽂으면 바로 통신됩니다.**

- **Tool calling** 때문에 쓴다고 봐도 무방합니다. tool calling과 tool 서버를 제공하여, LLM 모델이 자동으로 툴을 선택합니다.
- MCP는 **표준 규격**이라 선(연결)으로만 보기에는 애매합니다.

### MCP vs JSON-RPC

| 구분 | MCP (Model Context Protocol) | JSON-RPC |
| --- | --- | --- |
| **정체** | AI와 외부 환경을 잇는 **인프라 표준** | 데이터를 주고받는 **메시지 규격** |
| **역할** | 서버-클라이언트 수명 주기 관리, 도구 발견 | 함수 호출 요청 및 결과값 전달 |
| **비유** | 전화국과 통신망 전체 | 전화기 너머로 주고받는 한국어나 영어 |
| **관계** | 상위 개념(프레임워크) | 하위 수단(프로토콜) |

## 3. MCP 연결 방식

### Stdio — 같은 컴퓨터 안에서 바로 연결

Stdio는 MCP를 **로컬에서 사용할 때 기본으로 쓰는 방식**입니다. 이름 그대로 **표준 입출력(Standard Input/Output)** 을 사용합니다.

- 터미널에 입력하면 프로그램은 이를 `stdin`으로 읽습니다.
- 프로그램이 출력하면 터미널에 `stdout`으로 보냅니다.

MCP에서는 이 채널로 **AI 클라이언트와 MCP 서버가 JSON 메시지를 주고받습니다.** 같은 컴퓨터 안에서 AI 클라이언트가 MCP 서버 프로세스를 직접 실행하고, 그 프로세스의 `stdin/stdout`에 JSON을 쓰고 읽는 구조입니다. 별도의 포트나 HTTP 서버 없이 동작합니다.

**장점**
- 구성이 단순합니다. 네트워크·포트·도메인을 몰라도 동작하며, "이 바이너리를 Stdio MCP로 실행해 줘" 정도의 설정이면 충분합니다.
- 기본적으로 로컬에만 열려 있어 보안 측면에서 안전합니다(외부에서 접속할 엔드포인트가 없음).

**단점**
- 원격에서 접근하기 어렵습니다. 같은 머신의 클라이언트만 이 MCP 서버를 사용할 수 있어, 팀원과 공유하거나 서버에 올려 여러 사람이 쓰는 구조에는 맞지 않습니다.

### SSE — HTTP 위에서 지속적으로 메시지 흘리기

로컬 실험을 넘어 **서버에 배포해 여러 사람이 공유하는 MCP 서버**를 만들고 싶다면 **SSE(Server-Sent Events)** 방식을 사용합니다.

## 5. DevOps에서 AIOps로

대응 관계로 보면 다음과 같습니다.

| DevOps | AIOps |
| --- | --- |
| HTTP(프로토콜) | MCP |
| 서비스 | 에이전트 |
| DB | 온톨로지 |

DevOps는 파이프라인(`컨-서-레-엔`)처럼 **1차원 구조로 데이터를 하나하나 처리**합니다. 반면 AIOps에서는 Stream 같은 흐름으로는 에이전트에게 충분한 데이터를 공급하기 어렵습니다. 그래서 **Flow 같은 흐름으로, 데이터를 하나하나 보내는 대신 일괄적으로 보내야** 합니다.

> **배달에 비유하면, 주문자 4명의 음식을 배달기사 1명이 한 번에 전달하는 것이 Flow, 배달기사 4명이 1:1로 전달하는 것이 Stream입니다.**

- `langchain`(Stream) / `langgraph`(Flow) → AIOps 프레임워크
- 관련 키워드: 엔터프라이즈, job, 에이전트, 워크플로우(설계도), webhook

### 규칙 기반 vs 정책 기반

- **규칙 기반**: 기존 스프링 서비스
- **정책 기반**: 에이전트

게이트웨이에서 사용자의 요청이 정책 기반인지 규칙 기반인지 파악한 뒤, **정책 기반이면 오케스트레이터로 전달**해 알맞은 라우터 역할을 수행하게 하고, **규칙 기반이면 일반 서비스를 실행**합니다.

## 6. 에이전트(Agent)

> **에이전트 = LLM과 상호작용하며, 루프(자기가 사는 환경) 하에서 목표를 위해 도구(서로 연결하는 선)를 호출하는 최소한의 단위.**

- LLM(속성)과 도구(기능)의 집합이 에이전트입니다.
- 사용자를 위해 독립적으로 일하는 AI 시스템입니다.
- 프레임워크: `langchain`(Stream), `langgraph`(Flow)

에이전트에게는 툴로 라이브러리를 부여할 수 있습니다.

시스템을 자동화(에이전트가 관리)하려면, **벡터 DB를 에이전트가 직접 생성**하고 기존 PostgreSQL DB에 대한 임베딩도 에이전트가 수행하도록 설정해 둬야 합니다. 그래서 에이전트에게 라이브러리 등을 줍니다.

> **이는 "학습"이 아니라, 로봇에 칩을 넣듯 기능을 부여하는 방식입니다.**

기존 테이블을 에이전트가 스스로 벡터로 만들게 해야 하며, 터미널에서 에이전트에게 자신에게 맞는 벡터 DB를 만들라는 CLI를 입력합니다(임베딩도 마찬가지). 즉 **컨텍스트를 줘야** 자동화가 됩니다.

참고로 머신러닝에서의 "학습"은, 모델을 가져와 학습시키는 **파인튜닝**으로 이해하면 됩니다.

## 8. 상태 관리 모델 — 판독과 판별

상태 관리 모델로는 **Pydantic 모델**을 사용합니다. 에이전트의 역할을 다음 둘로 나눠 설계했습니다.

- **판독**: 결정 규칙
- **판별**: 분류 정책

예를 들어 `KoELECTRA`가 스팸메일일 확률을 알려주면(판별), `EXAONE`이 최종 결정을 내리는(판독) 식으로 진행합니다.

관련 개념: DDD/DEA, 허브-스포크(스타 구조), 리프(leaf), 휴리스틱 기반 판단(규칙인지 정책인지 굳이 판단할 필요가 없을 때).

## 10. ReAct 패턴과 fastMCP

MCP 라이브러리 중에서는 **fastMCP(프레임워크)** 를 사용할 예정입니다. MCP를 추상이라고 보면 fastMCP가 그 구현체이며, MCP는 타입 같은 존재입니다.

| 개념 | 비유 (웹 개발) | 비유 (AI 도구 개발) |
| --- | --- | --- |
| **규약 (Protocol)** | HTTP (데이터를 주고받는 규칙) | MCP (모델과 도구가 대화하는 규칙) |
| **도구 (Library)** | FastAPI / Flask | fastMCP |
| **결과물 (Server)** | 웹 API 서버 | MCP 서버 (도구 모음) |

관련 키워드: 리듀스(reduce), BullMQ.
